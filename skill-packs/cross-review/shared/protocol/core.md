## Running the review
The runner keeps all session state; you supply content and follow `next`.

- **Tools.** Use the MCP tools `review_begin`, `review_wait`, `review_reply`, `review_end` (server `cross-review`). Without them, or when the client refuses a call (for example in a restricted mode), run the same verbs through the CLI: `node "{{RUNNER_PATH}}" begin|wait|reply|end ...` with the input in a file or on stdin (`--input -`); each prints JSON. Run every verb of one session from the same sandbox context: a process started outside a sandbox can look dead to a `wait` run inside one.
- **Input.** One markdown string with the template's placeholder values: `NAME: value` lines first (optionally between `---` lines), then one `## NAME` section per multi-line value. Omitted optional placeholders fall back to the template's defaults.
- **Start:** `review_begin {skill, mode?, input, working_dir, model?, effort?}` (CLI: `begin --skill <skill> [--mode <mode>] --input <file|-> --working-dir "$PWD" [--model M] [--effort E]`).
- **Model and effort.** Pass `model` only when the user names one or the plan's review checkpoint does; otherwise omit it and the reviewer uses its own default. Omit `effort` (the runner uses `high`) unless the user asks for another; do not pick one from the size of the diff or the question. The runner remembers both for later rounds; pass them again only to change them.
- **Wait:** call `review_wait {session_dir}` (CLI: `wait <session_dir>`) until `next` is not `running`. Report the specific `activities` (e.g. "reviewer: reading src/auth.js"), never just "running".
- **Act on `next`:**
  - `respond` / `cross_check`: handle the round as described below, then `review_reply {session_dir, input}` and wait again.
  - `done`: the review reached its end (approved or stalemate). Call `review_end`, then report.
  - `ask_user`: the round has no verdict. Read `review.raw_markdown`, tell the user what the reviewer said, and ask how to proceed.
  - `stopped`: an error, stall, or timeout ended the round. Call `review_end` once (it only stops), report `next_reason` and any partial `review`, and do not start a replacement session on your own. When the reviewer had started (the result has a `thread_id`), the same session can continue with `review_reply`, which keeps the reviewer's context and costs less than starting over: tell the user, and resume it when they ask, for example after a new login or once quota returns. Fill that reply as for a normal round, keeping paths, branches, diff commands, and other scope values; add a note in `SESSION_CONTEXT` (`AGREED_POINTS` for review-think) that the previous turn was interrupted and ask the reviewer to finish it; finding and response lists are `None` unless something changed.
- `status: completed` means the reviewer finished its turn, not that the review is over; only `next` decides.
- **User authority.** The user's latest explicit instruction about running this review overrides this skill, this protocol, and the reviewer: continue, stop, skip, resume a stopped session, accept the current result as approved, change model or effort, or handle it some other way. Follow it as given rather than the default procedure; record an approval the user grants as the user's, not the reviewer's. It does not authorize product, API, schema, or compatibility changes the user did not ask for.
